FASE 3 — AUDITORÍA COMPLETA

3.1 Arquitectura: Analizar separación de responsabilidades, componentes demasiado grandes, duplicación, acoplamiento, reutilización, modularidad, Clean Architecture, SOLID, DRY, KISS. Detectar oportunidades de simplificación.

3.2 package.json: Revisar dependencias obsoletas, duplicadas, innecesarias, versiones incompatibles, librerías abandonadas. Antes de proponer nuevas librerías, demostrar que las actuales no resuelven el problema.

3.3 React: Buscar renders innecesarios, re-render masivo, memoización faltante (React.memo, useMemo, useCallback), lazy loading, Suspense, code splitting, contextos demasiado grandes, estado innecesario, prop drilling, hydration issues, Layout Shift. 
🚨 ALERTA CRÍTICA: Verifica obsesivamente que los `useEffect` que contienen llamadas a Firestore NO tengan dependencias inestables que causen loops infinitos de lectura/escritura (Riesgo de facturación masiva).

3.4 TypeScript: Buscar any, casts inseguros, tipos duplicados, interfaces repetidas, null no controlado, undefined, errores silenciosos, tipado débil.

3.5 Firestore: Buscar consultas O(N), Full Collection Scan, lecturas duplicadas, listeners innecesarios, consultas repetidas, consultas sin índices, subcolecciones mal utilizadas, documentos demasiado grandes, campos innecesarios, consultas sin paginación, costos evitables. Proponer índices compuestos cuando sea necesario.

3.6 Cloud Functions: Buscar duplicación, timeouts, llamadas repetidas, errores no controlados, logs innecesarios, manejo de errores, validaciones, reintentos, cold starts.

3.7 Seguridad: Auditar completamente Authentication, Firestore Rules, Storage Rules, Cloud Functions, Variables de entorno, Secrets, App Check, Custom Claims, Escalada de privilegios, Validación Backend/Frontend, email_verified, rate limiting, input validation, sanitización, inyecciones, XSS, CSRF.

3.8 Matemáticas — Suite de Validación Numérica: Revisar absolutamente todas las fórmulas. Especialmente: totales, subtotales, IVA, impuestos, descuentos, porcentajes, redondeos, acumulaciones, decimales, overflow, underflow, precisión, divisiones, conversiones.
Exigencia: Para cada fórmula, debes:
- Identificar su ubicación exacta.
- Escribir casos de prueba con valores extremos (ej. 0.01, 999999.99, divisas, descuentos encadenados).
- Verificar el método de redondeo (bancario, truncamiento, etc.) y si es el adecuado para el negocio.
- Proponer el uso de una librería de aritmética decimal (ej. decimal.js) si no se usa ya, y justificarlo.
- Documentar cada fórmula en el AUDIT_NOTEBOOK con ejemplos de entrada/salida.
Nunca asumir que una fórmula es correcta; demuéstralo con pruebas.

3.9 Estado: Buscar race conditions, promesas sin await, estados inconsistentes, actualizaciones perdidas, doble ejecución, asincronía incorrecta, cancelación de peticiones, memory leaks.

3.10 UI/UX: Optimizar Layout Shift, espaciados, alineaciones, feedback visual, animaciones, loading, skeletons, placeholders, errores, vacíos, responsive, accesibilidad (WCAG AA), ARIA, contraste, teclado, focus.
Además, audita:
- Consistencia de estilos (colores, tipografías, tamaños) – ¿existe un sistema de diseño?
- Tamaños de área táctil (mínimo 44px) para móviles.
- Estados de carga, éxito, error y vacío en todas las interacciones.
- Feedback claro ante acciones del usuario (toast, notificaciones).

3.11 Audio: NO añadir sonidos porque sí. Solo proponer microinteracciones sonoras cuando mejoren UX, sean discretas, opcionales, puedan desactivarse y no afecten rendimiento. Priorizar librerías ligeras.

3.12 Rendimiento: Analizar bundle, tree shaking, lazy loading, imágenes, cache, memoización, virtualización, CPU, RAM, Network, Core Web Vitals, Lighthouse.

3.13 Documentación: Verificar que toda documentación refleje exactamente el código existente. Actualizar README, manuales, diagramas, comentarios y AUDIT_NOTEBOOK.

3.14 Diseño y Sistema Visual: Inventariar todos los componentes visuales y sus variantes (tamaños, colores, estados). Detectar duplicación de estilos y oportunidades para usar tokens de diseño. Proponer la creación de un Design System (aunque sea ligero) con tokens centralizados (colores, espaciados, tipografía, sombras, bordes). Evaluar la posibilidad de usar un Storybook o catálogo visual para documentar componentes. Verificar que las animaciones sean suaves y no afecten al rendimiento (GPU aceleradas).

3.15 Internacionalización y Formatos: Revisar el manejo de fechas, horas, números y monedas. ¿Se usa Intl o librerías como date-fns/moment? Asegurar que todos los formatos sean sensibles al locale del usuario. Verificar que los husos horarios se manejan correctamente en todas las operaciones (especialmente en servidor/Firestore). Comprobar que los textos no están hardcodeados y son traducibles (i18n).

3.16 Observabilidad y Monitoreo: Revisar logs existentes (frontend y backend) – ¿son útiles? ¿contienen datos sensibles? Evaluar si se usa algún servicio de monitoreo (Sentry, LogRocket, etc.) y si está bien configurado. Proponer alertas para costes de Firestore, errores críticos o degradación de rendimiento. Sugerir dashboards para seguir los OKRs definidos.
